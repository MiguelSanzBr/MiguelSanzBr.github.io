Evig · team of 5 engineers · built from scratch (69% of commits)

WhatsApp messaging gateway in Go

Customer messages on WhatsApp could not be lost, duplicated or delivered out of order.

900 msg/min · 0% failures · p95 1.05 s · 9,901/9,901

problem

Messages from the CRM and the AI agents had to go out over WhatsApp without duplicates, without losses and in conversation order, even with retries, deploys and worker crashes along the way.

decision

Ports & adapters, a PostgreSQL outbox with FOR UPDATE SKIP LOCKED, 3-layer idempotency and per-conversation ordering. 100% coverage gate, gosec and govulncheck.

result

900 msg/min for 10 min, 0% failures, p95 of 1.05 s, 9,901/9,901 delivered in the k6 load test with a mocked Meta API: it measures the gateway, not WhatsApp end to end. The simulation at the top of the page lets you take down a worker.

trade-offs and limits

Outbox in PostgreSQL itself, no broker at first and an interface to swap one in later: fewer moving parts to run, with the database as the bottleneck. In the test, the ceiling came from RDS CPU (70% gate at 20 msg/s), well above the real production peak (41 messages in 5 min). A reaper was left open: if a worker dies mid-send, the message only returns to the queue when its 5 min lease expires, so it can be delayed up to 5 min, but it is not lost. Meta's rate limit is still handled reactively.

Bugs, incidents and security flaws I diagnosed and fixed. Click to see symptom, root cause and fix; each one comes from a commit of mine.

Evig · jun 2026The same WhatsApp message arrived several timesatomic lock in a shared cache
symptom
Users received the same message more than once in production, but the database showed no duplicate execution.
root cause
The anti-duplication lock used a file cache, and Cloud Run runs 1 to 100 instances, each with its own disk: each one only saw its own lock.
fix
Atomic lock (Cache::add) in a shared PostgreSQL cache, a second content lock (sha256, 24 h), no resend on timeout and removal of a legacy path that also sent messages.
  • Laravel
  • Cloud Run
  • PostgreSQL
  • WhatsApp
Evig · sep 2026News campaign sent twiceretry_after above the job timeout
symptom
The same campaign reached the same user twice.
root cause
The queue's retry_after (90 s) was shorter than the job's run time: another worker picked up the job while the first was still sending.
fix
retry_after of 900 s, above the worker timeout, a per-user-and-campaign lock, a batch named after the campaign, 30/120/300 s backoff and a metric for skipped duplicate sends.
  • Laravel Queues
  • Supervisor
Evig · sep 2026Deploys took the CRM down with permission deniedidempotent grants on deploy
symptom
After a deploy, the CRM returned 500 with SQLSTATE[42501].
root cause
Migrations ran under another role, which owned the new tables, and ALTER DEFAULT PRIVILEGES without FOR ROLE only covers objects of the role that ran the command.
fix
An idempotent command that grants DML only, right after migrate, default privileges for the migration role and a deploy that fails early on bad config. Documented in a runbook.
  • PostgreSQL
  • Laravel
  • deploy
Evig · sep 2026One company's admin could edit another company's employeescompany scope on every lookup
symptom
Any admin who knew the id could change the email, CPF and phone of another company's employees, or delete them.
root cause
The update and destroy routes looked the employee up by id without checking the company (IDOR).
fix
Lookups always scoped to the caller's company, 404 for outside ids, a review of the bulk endpoints and regression tests for every path.
  • Laravel
  • multi-tenant
  • PHPUnit
Evig · jun–jul 2026Webhooks could be forgedsecret from the environment + constant-time comparison
symptom
