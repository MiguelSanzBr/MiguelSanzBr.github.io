Evig · designed and built from scratch (69% of commits)

WhatsApp messaging gateway in Go

No customer message on WhatsApp could be lost, duplicated or delivered out of order.

900 msg/min · 0% failures · p95 1.05 s

problem

Messages from the CRM and the AI agents had to go out over WhatsApp without duplicates, without losses and in conversation order, even with retries, deploys and several workers in parallel.

decision

Ports & adapters, a PostgreSQL outbox with FOR UPDATE SKIP LOCKED, 3-layer idempotency (webhook receipt, turn dispatch and outbox dispatch) strict ordering per conversation (lane with fencing token) and per recipient in the outbox. 100% coverage gate on every PR; gosec and govulncheck in a nightly job.

result

900 msg/min for 10 min, 0% failures and a p95 of 1.05 s from webhook to reply, in the k6 load test with fixed-delay mocks (200 ms for the AI, 550 ms for Meta): the gateway’s own p95 overhead was 303 ms. 9,901/9,901 delivered over the full run (11 min, including warm-up). It measures the gateway, not WhatsApp end to end.

trade-offs and limits

  • Outbox in PostgreSQL itself, no broker yet, behind an interface that allows swapping one in: fewer moving parts, with the database as the bottleneck.
  • Load-test ceiling: RDS CPU (70% gate at 20 msg/s; 15 msg/s is the highest confirmed rate, the 15–20 range wasn’t refined), far above the real production peak (41 messages in 5 min).
  • One suspect was the status lookup by provider_message_id, which had no index (Seq Scan in EXPLAIN); a teammate added the index later (migration 015), but no new load run has measured it yet.
  • No reaper yet: if a worker dies mid-send, the message stays in sending and isn’t resent automatically, because there’s no way to know whether Meta already got it. Once its 5-min lease expires, the message merely stops holding back that customer’s next ones. I’d rather resend by hand, after checking with Meta (no written runbook step yet), than risk a duplicate; try it by taking down a worker in the simulation at the top.
  • Meta’s rate limit is still handled reactively.

Problems I fixed 11

Bugs, incidents and security flaws I diagnosed and fixed. Open one to see the symptom, root cause and fix; each one is backed by one of my commits.

Evig · Jun 2026 The same WhatsApp message arrived several times atomic lock in a shared cache
symptom
Users received the same message more than once in production, but the database showed no duplicate execution.
root cause
The anti-duplication lock used a file cache, and Cloud Run runs 1 to 100 instances, each with its own disk: each one only saw its own lock.
fix
Atomic lock (Cache::add) in a shared PostgreSQL cache, a second content lock (sha256, 24 h), no resend on timeout and removal of a legacy path that also sent messages.
  • Laravel
  • Cloud Run
  • PostgreSQL
  • WhatsApp
Evig · Sep 2026 News campaign sent twice retry_after above the job timeout
symptom
The same campaign reached the same user twice.
root cause
The queue’s retry_after (90 s) was shorter than the job’s run time: another worker picked up the job while the first was still sending.
fix
retry_after of 900 s, above the worker timeout, a per-user-and-campaign lock, a batch named after the campaign, 30/120/300 s backoff and a metric for skipped duplicate sends.
  • Laravel Queues
  • Supervisor
Evig · Sep 2026 Deploys took the CRM down with permission denied idempotent grants on deploy
symptom
After a deploy, the CRM returned 500 with SQLSTATE[42501].
root cause
Migrations ran under another role, which owned the new tables, and ALTER DEFAULT PRIVILEGES without FOR ROLE only covers objects of the role that ran the command.
fix
An idempotent command that grants DML only, right after migrate, default privileges for the migration role and a deploy that fails early on bad config. Documented in a runbook.
  • PostgreSQL
  • Laravel
  • deploy
Evig · Sep 2026 One company’s admin could edit another company’s employees company scope on every lookup
symptom
Any admin who knew the ID could change the email, CPF and phone of another company’s employees, or delete them.
root cause
The update and destroy routes looked the employee up by ID without checking the company (IDOR).
fix
Lookups always scoped to the caller’s company, 404 for outside IDs, a review of the bulk endpoints and regression tests for every path.
  • Laravel
  • multi-tenant
  • PHPUnit
Evig · Jun–Jul 2026 Webhooks could be forged secret from the environment + constant-time comparison
symptom
The webhook signature used a secret hard-coded in the source, and the internal endpoint only checked that an authorization header was present.
root cause
Placeholder values in the code, with no config validation at boot.
fix
Secret from the environment (empty = reject), internal key compared with crypto/subtle, body capped at 1 MiB, boot fails without secrets. Later: signed tokens with single-use nonces, events older than 5 min dropped and rate limiting on public routes.
